Apps Webview & Híbridos, do jeito spec-driven

Como projetar, especificar e construir apps desktop cuja interface é HTML/CSS/JS renderizado num WebView embutido, com um núcleo nativo cuidando de janela, bandeja, SO e segredos. Vale para pywebview, Tauri, Electron, Wails e afins — o framework é detalhe; o contrato e os estados são o que seguram o app.

host ↔ ponte ↔ renderer contrato primeiro UI = render(estado) fronteira de confiança
§ 01 · fundamento

O modelo mental

Um app híbrido tem duas metades conversando por uma ponte. O host é nativo e poderoso; o renderer é web e apresenta; a ponte é a fronteira por onde tudo passa — e onde tudo é validado.

Princípio central. O renderer é “burro e desconfiado”: só apresenta e coleta interação. Toda lógica sensível, segredo e acesso ao SO vivem no host. Tudo que cruza a ponte é dado não-confiável.

§ 02 · decisão

Quando escolher (e quando não)

Escolha webview/híbrido quando: a UI é rica/visual e você domina web; quer um só código de UI (e talvez reaproveitar na web); quer iterar rápido no visual (hot-reload, DevTools).

Prefira UI nativa (Qt, WinUI, SwiftUI, Tkinter) quando latência/memória são críticas, você precisa de aparência “pixel-nativa”, ou o app é só formulários simples.

WebView do SO usa o navegador já instalado (WebView2 no Windows, WKWebView no macOS, WebKitGTK no Linux): binário menor, mas depende do runtime existir/atualizar. Chromium embutido renderiza igual em toda máquina, ao custo de tamanho.

§ 03 · arquitetura

Host, renderer e a ponte

CamadaFazNão faz
Hostjanela, bandeja, SO, FS, rede, cripto, segredos, regra de negóciorenderizar UI, confiar no renderer
Ponteexpor comandos, emitir eventos, serializar, validar entradalógica de negócio
Rendererapresentação, estado de UI, chamar comandos, tratar eventosguardar segredo, acessar SO direto

Dois sentidos de comunicação

  • Comando (renderer → host): “faça X”, geralmente async e retorna resultado — getUsage(), saveSettings(x), minimize().
  • Evento (host → renderer): “algo mudou”, push assíncrono — onData(snapshot), onError(e).

Modelo de concorrência

  • O renderer é single-thread; nunca bloqueie a UI.
  • O host faz trabalho pesado (rede/disco) fora da thread de UI e, ao terminar, empurra um evento ou responde ao comando.
  • Padrão robusto: um poller mantém um snapshot atual; o renderer lê o snapshot (rápido) e/ou recebe eventos quando ele muda.
§ 04 · método

Spec-Driven: o quê e porquê

Spec-driven development é escrever a especificação verificável antes do código: o que o sistema faz, quais estados existem, qual o contrato entre as partes e como saber que está pronto. O código vira a implementação de uma spec, não o lugar onde as decisões acontecem ad-hoc.

Por que casa com apps híbridos. A ponte é um contrato entre dois mundos; a UI tem muitos estados fáceis de esquecer; segurança e empacotamento têm requisitos que precisam ser explícitos e checados.

Benefícios: menos retrabalho, testes derivados da spec, onboarding rápido, e um contrato estável mesmo trocando o framework (Electron → Tauri) sem reescrever a UI.

§ 05 · especificação

Anatomia de uma spec completa

Sete blocos, cada um curto e verificável.

#BlocoContém
1Produtoproblema/usuário/valor · escopo (in/out) · métricas
2Funcionalfeatures com ID · fluxos · casos de borda · regras puras
3UItelas · todos os estados (loading/empty/error/ok/especiais) · tema · responsividade · a11y
4Contratocomandos, eventos, envelope de erro, versão (ver §06)
5Não-funcionalsegurança · performance · persistência · atualização
6EmpacotamentoSOs · runtime · instalador · assinatura
7Definition of Donechecklist por feature + qualidade (testes, review, build)

Estados são obrigatórios. Liste, para cada tela, loading · empty · error · success mais os estados especiais do domínio. Tela em branco num estado não previsto é o bug mais comum desse modelo.

§ 06 · o coração

O contrato da ponte — projete primeiro

Desenhe o contrato antes da UI e do host. Trate como uma API: versione, valide, padronize erros.

Envelope de resposta padronizado

// sucesso
{ "ok": true,  "data": { /* payload */ } }
// erro
{ "ok": false, "error": { "code": "TOKEN_MISSING", "message": "texto amigável" } }

Snapshot orientado a estado

O renderer nunca “calcula” — ele renderiza um snapshot que o host entrega pronto:

{
  "state": "ok",          // "loading" | "empty" | "error" | "ok"
  "message": null,        // preenchido em empty/error
  "items": [ /* ... */ ],
  "updatedAt": "2025-01-01T10:22:00Z",
  "meta": { "version": 1 }
}

Assim a UI vira uma função pura do estado: UI = render(snapshot). Adicionar um estado novo = mudar o host + um branch no render().

Catálogo de comandos e eventos

COMANDOS (renderer → host)          EVENTOS (host → renderer)
  getSnapshot() -> Snapshot           onSnapshot(Snapshot)
  refresh()     -> Snapshot           onError(Error)
  saveSettings(Settings)              onSettingsChanged(Settings)
  window.minimize() / hide()
  window.resize(w, h)

Boas práticas de contrato

  • Nomes estáveis e versionados (meta.version); mudança que quebra → suba a versão.
  • Valide toda entrada no host (nunca confie em tipos vindos do JS).
  • Erros como dados (envelope), não exceções atravessando a ponte.
  • Idempotência onde fizer sentido.
  • Sem segredo no snapshot — só o necessário para exibir.
§ 07 · estrutura

Organização de pastas

Muitos arquivos pequenos, organizados por feature/domínio (não por tipo), com a lógica pura isolada para testar sem UI nem rede.

meu-app/
├─ src/
│  ├─ host/                  # núcleo nativo (backend)
│  │  ├─ main.*              # cria janela, bandeja, inicia loops
│  │  ├─ bridge/             # a PONTE: comandos/eventos, validação
│  │  │  ├─ commands.*
│  │  │  └─ contract.*       # tipos/schema (fonte da verdade)
│  │  ├─ services/           # rede, FS, cripto, integrações
│  │  ├─ domain/             # lógica pura, testável
│  │  └─ platform/           # tray, notificações, autostart
│  └─ web/                   # renderer (frontend)
│     ├─ index.html
│     ├─ styles/             # tokens.css, themes.css
│     ├─ components/         # por feature
│     ├─ lib/                # bridge-client, render, helpers
│     └─ state/
├─ assets/                   # ícones, imagens, fontes
├─ tests/{unit,contract,e2e}/
├─ packaging/                # build, instalador, assinatura
├─ docs/{SPEC,CONTRACT,ARCHITECTURE}.md
├─ .gitignore  ·  LICENSE  ·  README.md
FrameworkOnde fica o hostOnde fica a ponte
pywebviewsrc/host/main.pybridge/api.py (classe Api = comandos)

Electronmain/main.jspreload.js + contextBridge

Padrão comum: um lugar para o host, um para a web, um para a ponte, um para lógica pura, um para empacotamento. Só mudam os nomes.

§ 08 · interface

Padrões de UI e estado

  • UI como função do estado: render(snapshot) decide tudo; sem estado escondido no DOM.
  • Máquina de estados de tela: loading → (ok | empty | error), cada um com layout próprio.
  • Design tokens em CSS (--color-*, --space-*); trocar tema = trocar variáveis.
  • Tema: claro/escuro/auto; persista a escolha; ofereça toggle.
  • Responsividade: unidades relativas, flex/grid, rolagem própria em overflow; nada de tamanho fixo que corte conteúdo.
  • Acessibilidade: HTML semântico, foco visível, contraste, prefers-reduced-motion.
  • Feedback: comando que demora mostra estado e trata erro.
§ 09 · segurança

A fronteira de confiança

O renderer roda conteúdo web: trate-o como potencialmente hostil (XSS, dependência comprometida).

  • CSP restritiva — sem unsafe-inline para script; idealmente tudo local/embutido.
  • Isolamento de contexto — sem acesso direto a Node/SO no renderer (Electron: contextIsolation:true, nodeIntegration:false, preload+contextBridge; Tauri: allowlist mínima; pywebview: exponha só o necessário no js_api).
  • Valide toda entrada vinda do renderer (tipos, faixas, tamanho).
  • Segredos só no host — nunca no HTML/JS nem no snapshot; use o cofre do SO (DPAPI/Keychain/libsecret).
  • Sem eval/innerHTML com dado dinâmico não sanitizado.
  • Superfície mínima de comandos; assine o binário; fixe versões; audite terceiros.

Mnemônico. O renderer nunca é dono de nada perigoso — janela, arquivo, segredo e rede são do host, acessados por comandos explícitos e validados.

§ 10 · distribuição

Empacotamento e distribuição

  • Bundler por framework: PyInstaller/Briefcase, tauri build, electron-builder/Forge.
  • Dependência de runtime: se usa WebView do SO, documente/instale o runtime (ex.: WebView2 no Windows) — ou embuta, se der.
  • Assinatura de código: evita avisos do SO e falsos-positivos de antivírus (comuns em “onefile” não assinado). Sem verba de assinatura, prefira onedir a onefile.
  • Instalador: MSI/NSIS/.pkg/AppImage; atalhos; opção de iniciar com o sistema.
  • Auto-update: Tauri/Electron têm updaters; senão, cheque versão e baixe manual.
  • Tamanho: WebView do SO ≪ Chromium embutido; faça tree-shaking do frontend.
  • Distribuição: binários grandes vão em Releases, não no repositório git.

§ 12 · processo

Fluxo spec-driven, passo a passo

1.  SPEC        docs/SPEC.md — escopo, features, estados
2.  CONTRATO    docs/CONTRACT.md — comandos, eventos, envelope, snapshot
3.  ESQUELETO   estrutura de pastas; stubs de comando retornando mock
4.  UI-MOCK     render(snapshot) para TODOS os estados, com dados falsos
5.  DOMÍNIO     lógica pura com TDD (RED → GREEN → REFACTOR)
6.  SERVIÇOS    rede/FS/cripto no host; preenche o snapshot de verdade
7.  PONTE       comandos/eventos reais; valida entradas; testes de contrato
8.  NÃO-FUNC.   segurança, persistência, tema, responsividade, a11y
9.  EMPACOTE    build + instalador + runtime + assinatura; teste em máquina limpa
10. REVIEW      code review + Definition of Done; E2E dos fluxos-chave

Repare na ordem. A UI-mock (4) vem antes do backend real: como a UI é função do snapshot, você desenha e aprova o visual com dados falsos e só depois “liga o cano”.

CONTRACT.md (esqueleto)

# Contrato da Ponte — v1

## Envelope
  sucesso: { ok:true, data:<T> }
  erro:    { ok:false, error:{ code, message } }

## Snapshot
  { state:"loading|empty|error|ok", message, items[], updatedAt, meta:{version} }

## Comandos (renderer → host)
  | nome         | args         | retorno  | erros              |
  | getSnapshot  | —            | Snapshot | —                  |
  | refresh      | —            | Snapshot | NETWORK, AUTH      |
  | saveSettings | Settings     | Settings | VALIDATION         |
  | window.resize| w:int, h:int | void     | —                  |

## Eventos (host → renderer)
  | onSnapshot | Snapshot | poller atualizou |
  | onError    | Error    | falha assíncrona |

Definition of Done (checklist)

[ ] Spec e contrato atualizados
[ ] Todos os estados de UI implementados e testados
[ ] Entradas validadas no host; erros no envelope padrão
[ ] Sem segredo no renderer; CSP/isolamento aplicados
[ ] Testes unit + contract + e2e verdes; cobertura ≥ meta
[ ] Build empacotado testado em máquina limpa
[ ] README + screenshots + licença
§ 14 · cuidado

Anti-padrões e armadilhas

  • Lógica de negócio no renderer. Migração de framework quebra tudo; segredo vaza.
  • Confiar em dados do renderer sem validar no host.
  • Snapshot que a UI precisa “recalcular”. Entregue pronto para exibir.
  • Esquecer estados (só o “sucesso”): tela em branco em erro/vazio.
  • Tamanho fixo sem rolagem → conteúdo cortado ao redimensionar.
  • CSP permissiva / innerHTML com dado externo → XSS.
  • Chamar comando a cada frame (ex.: em resize) sem throttle/requestAnimationFrame.
  • Binário “onefile” não assinado e surpresa com antivírus/SmartScreen.
  • Bloquear a thread de UI com rede/disco no renderer.
  • Commitar build/segredos/estado local no git.
§ 15 · aprofundar

Ecossistema e leituras

  • Frameworks: Electron, Tauri, pywebview, Wails, Neutralino, NW.js, CEF.
  • Motores web do SO: WebView2 (Win), WKWebView (macOS), WebKitGTK (Linux).
  • Bridges/segurança: Electron contextBridge/preload; Tauri commands + allowlist; pywebview js_api.
  • Empacotadores: electron-builder/Forge, tauri build, PyInstaller/Briefcase.
  • Testes E2E: Playwright, WebdriverIO, tauri-driver.
  • Conceitos: IPC e fronteira de confiança, JSON Schema/contract testing, máquinas de estado de UI, design tokens, code signing, auto-update.

Em uma frase. Projete o contrato e os estados primeiro, mantenha o renderer burro e desconfiado, isole a lógica pura para testar, e trate a ponte como a API que segura o app inteiro — o framework vira detalhe.

Guia de referência genérico · host ↔ ponte ↔ renderer · spec-driven · aplicável a pywebview, Tauri, Electron, Wails e afins.
